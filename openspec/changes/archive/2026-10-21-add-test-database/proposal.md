# Proposal

## Why

The API's integration tests run against the dev database, so they depend on how long ago it was seeded and on what dev work left in it. The seed dates everything from `CURRENT_DATE` when it loads, so after a few days its full day has moved or passed. The `full_day` fixture then skips its tests ("reset the database"), and assertions that compute today from the wall clock drift from the data. The phase 4 eval suite (`add-eval-harness`, paused at task 3.2) would inherit the same coupling: it creates per-run schemas inside the dev database, and its leftover sweep could drop another session's schemas.

Tests need a database that exists only for tests, holding a seed for a fixed day. Two pieces of research for this change (Python/Postgres testing practice, and how agent benchmarks reset their environments: tau-bench, AppWorld, AgentBench, Inspect AI) agree. Testing against the developer's database is an anti-pattern. Each test run should start from a known state with a pinned "today".

This belongs to **phase 4**, as groundwork for `add-eval-harness`, and it takes precedence over it. It stays within the frozen scope: no tool, feature or agent behavior changes. Only the dev environment, the seed's date source and the API's integration test fixtures change.

## What Changes

- **A test-only PostgreSQL service in the dev environment.**
  - It uses the same image and tag as the dev `postgres` service, with data on `tmpfs` and durability settings off, so every start is empty and fast.
  - It has its own role and password, generated by `init-env.sh`.
  - It publishes no host port.
  - The `dev` service receives only its URL, as a new `TEST_DATABASE_URI`.
- **The seed takes its run day as a parameter.**
  - The generated `seed.sql` reads the day from a session setting, and falls back to the current date in `America/Sao_Paulo` when the setting is absent.
  - The dev reset, the first-start init script and the simulator keep today's behavior unchanged. Tests pass a fixed day.
- **A fixed seed day for tests.** It is one constant shared by the test fixtures: Monday 2026-03-09. Days +3..+5 then fall on 12–14 March, with no holiday.
- **The API's integration tests move to the test database.**
  - At the start of each pytest session, they load the schema and the seed for the fixed day.
  - They use `FixedClock(seed day)` instead of `SystemClock`.
  - The "full day" is the known date `seed day + 3`, not a query that skips when the seed has aged.
  - Without `TEST_DATABASE_URI` they are skipped, as today without `DATABASE_URI`.
- **Documentation:**
  - `AGENTS.md` (services, environment, the test database);
  - `.devcontainer/db/README.md` (the seed-day parameter, and which database tests use);
  - `.devcontainer/.env.example`.

Out of scope:
- **The CI workflow.** `add-ci-eval-gate` uses a `services: postgres` container with the same image and the same fixtures.
- **Moving the eval suite to the test database.** That is a follow-up edit to `add-eval-harness`, decision 3, after this change lands.

## Capabilities

### New Capabilities
- `test-database`: the isolated PostgreSQL that tests run against: how it is provided in the dev environment, how a test session loads it with a fixed seed day, and what tests may assume about it.

### Modified Capabilities
- `dev-seed-data`: the run day is a parameter. Seeded dates are relative to that day, which defaults to the current date in `America/Sao_Paulo`, so the same file gives a fresh dev seed or a pinned test seed.

## Impact

- **Dev environment:**
  - `.devcontainer/compose.yaml`: the new service, and `TEST_DATABASE_URI` on `dev`;
  - `.devcontainer/init-env.sh` and `.devcontainer/.env.example`: the new password;
  - a small init script for the test service;
  - the dev container must be rebuilt once.
- **Seed:** `.devcontainer/db/generate_seed.py` and the regenerated `seed.sql`. Every `CURRENT_DATE` becomes the parameterized day. Rows are unchanged for a seed applied on the same day.
- **API tests:** `apps/api/tests/integration/conftest.py` (environment variable, session seeding, removal of the `full_day` query) and the tests that read `SystemClock(...).today()` (`repositories/test_repositories.py`, `agents/test_tools.py`).
- **No change** to app code, runtime settings, the dev database's contents or the simulator.
- **Known limit:** column defaults such as `created_at` keep the server's real `now()`. No business rule reads them.
