# Proposal

## Why

Phase 2's "done when" asks to explain any conversation. To do that, Langfuse must show what the customer said, what the model answered and what each tool received and returned. It must also be possible to trace a Kibana latency spike back to its trace. Today neither works. Agent spans deliberately carry no content (`add-agent-spans` deferred content capture until there was a redaction step), and the Collector exports traces to Langfuse only. Elasticsearch has been running since `add-elastic-stack` but receives nothing.

The two backends have different jobs and need different data. Langfuse is the LLM view, where the maintainer reads and annotates conversations in phase 3, so it needs the content. Elasticsearch is the infra view (latency, errors, service map), so it does not need any customer text. Customer data should therefore reach Elasticsearch only after redaction. The redaction belongs in the Collector, not in the app: the app emits one set of spans, and each pipeline decides what leaves the dev network for which backend.

This is **phase 2 (instrumentation), step B, second change**. It stays within the frozen scope. It adds no tool and does not change agent behavior. The app only adds attributes to spans it already emits.

## What Changes

- **Content capture in the API**, behind a new `TELEMETRY__CAPTURE_CONTENT` switch that is off by default:
  - `chat` spans carry the messages sent to the model, the system instructions and the model's answer, as `gen_ai.input.messages`, `gen_ai.system_instructions` and `gen_ai.output.messages` (GenAI semconv, JSON).
  - `invoke_agent` spans carry the turn's customer message and the agent's replies.
  - `execute_tool` spans carry `gen_ai.tool.call.arguments` and `gen_ai.tool.call.result`.
  - `execute_tool` spans of the tools that take a phone carry it, normalized to E.164, in a dedicated attribute `fornada.customer.phone`. A phone that fails normalization is left out.
  - **BREAKING (spec):** the `agent-tracing` requirement "Spans carry no conversation content" becomes "content only when the capture switch is on". Client spans keep carrying no content.
- **Fan-out in the Collector:** a second traces pipeline that takes the same OTLP receiver and exports to Elasticsearch through the EDOT `elasticsearch` exporter (OTel mapping mode), with the `elasticapm` processor and connector that Kibana APM needs.
- **Redaction in the Elasticsearch pipeline only:** a `transform` processor deletes every content attribute and replaces `fornada.customer.phone` with a salted SHA-256 hash, so Kibana can still group spans by customer. The Langfuse pipeline stays unchanged and receives the content.
- **Dev environment plumbing:**
  - A dedicated Elasticsearch user with write-only permissions for the Collector, created by `elasticsearch-setup`.
  - Two new secrets in `.devcontainer/.env`, generated by `init-env.sh`: that user's password and the hash salt. Both are passed only to the Collector, plus `elasticsearch-setup` for the password.

**Done when:** the same trace, found by its trace id, shows up in Langfuse with the message text, tool arguments and phone in clear, and in Kibana APM with none of the content attributes and with `fornada.customer.phone` only as a hash.

Out of scope:
- Logs and metrics pipelines, `LoggerProvider`, `MeterProvider`: the next step B change.
- Presidio and PII detection inside free text: phase 6. A phone typed inside a message is not hashed here. It is removed along with the message.
- `langfuse.*` attributes in the Langfuse pipeline, such as copying `fornada.prompt.version` to `langfuse.version`. They may come in a later change.
- Collector spans or filters for the client services (the "8b" idea).
- Tool definitions on spans.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `agent-tracing`: content attributes on `invoke_agent`, `chat` and `execute_tool` spans when capture is on; the phone attribute on tool spans; the no-content requirement now applies only when capture is off.
- `telemetry-collector`: a second traces pipeline exports to Elasticsearch, with the redaction rules. The Langfuse copy keeps the content, and each backend's outage leaves the other one unaffected. The Elasticsearch export authenticates with its own least-privilege user.
- `app-config`: the `TELEMETRY__CAPTURE_CONTENT` setting.

## Impact

- `apps/api`:
  - `core/config.py`: new setting.
  - `agents/attendant/tracing.py`: attribute names.
  - `agents/attendant/nodes.py` and `attendant.py`: set the content attributes.
  - `agents/attendant/tools.py`, or the tool wrapper: set the phone attribute.
  - Tests for every new attribute and for the capture switch.
  - Root `.env.example` gets the new setting.
- `.devcontainer/otel-collector/config.yaml`: new exporter, processors, connector and pipelines. **Core:** the pipelines and the `transform` statements are written by the maintainer (`TODO(human)`).
- `.devcontainer/compose.yaml`:
  - Collector environment: Elasticsearch user, password and salt.
  - `elasticsearch-setup`: creates the role and the user.
  - The Collector starts after `elasticsearch-setup`.
- `.devcontainer/init-env.sh` and `.devcontainer/.env.example`: two new secrets.
- `AGENTS.md`: Collector section, covering the fan-out and how to check redaction.
- Data: Langfuse now stores customer text and phones from simulated conversations. That is acceptable in dev with fake data, and is recorded for the phase 7 LGPD map. Elasticsearch disk use grows with the APM indices.
- Cost: no token cost. Collector CPU and memory grow slightly, and Elasticsearch's 512 MiB heap gets its first real load.
