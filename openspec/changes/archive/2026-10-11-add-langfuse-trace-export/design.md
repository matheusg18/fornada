# Design

## Context

- The Collector (EDOT 9.5.5, Collector core v0.161.0) runs one traces pipeline: `otlp` receiver → `debug` exporter (`.devcontainer/otel-collector/config.yaml`). The API exports to it over OTLP/HTTP (`add-app-tracing`).
- Langfuse 4.53.0 (`langfuse-web`, port 3000 on the compose network) ingests OTLP/HTTP (protobuf or JSON, no gRPC) at `/api/public/otel`, so traces go to `/api/public/otel/v1/traces`. Auth is HTTP Basic with `public_key:secret_key`. Without the `x-langfuse-ingestion-version: 4` header, OTLP data can take up to 10 minutes to show up in v4.
- The dev Langfuse project and its keys are created on first start from `LANGFUSE_INIT_PROJECT_PUBLIC_KEY`/`SECRET_KEY`, which compose reads from `LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY` in `.devcontainer/.env`. `init-env.sh` (host, `initializeCommand`) creates that file once and exits if it exists.
- The EDOT component list for 9.5.5 includes `otlphttpexporter` and `headerssetterextension`, `bearertokenauthextension`, `apikeyauthextension`, but **not** `basicauthextension`.
- AGENTS.md puts "the pipelines in the Collector config" in core: the maintainer writes the pipeline; credentials and compose are periphery.

## Goals / Non-Goals

**Goals:**
- One authenticated `otlphttp/langfuse` exporter in the traces pipeline, verified end to end with the SERVER span from `add-app-tracing`.
- The credential is generated and wired without manual steps, also for an existing `.devcontainer/.env`.

**Non-Goals:**
- Processors (redaction, filtering, batching tweaks), Elasticsearch, logs/metrics pipelines: step B.
- Making the spans look good in Langfuse (session id, `gen_ai.*`, observation types): the next step A changes. For now the trace shows up as plain spans, with attributes under `metadata.attributes`.

## Decisions

### 1. Auth as a precomputed `Authorization` header, not an auth extension

The exporter sets `headers: { Authorization: "Basic ${env:LANGFUSE_OTLP_AUTH}", x-langfuse-ingestion-version: "4" }`, where `LANGFUSE_OTLP_AUTH` is `base64(public_key:secret_key)`.

- *Alternative: `basicauth` extension* with `${env:LANGFUSE_PUBLIC_KEY}`/`${env:LANGFUSE_SECRET_KEY}`, no base64 step. Rejected: not in the EDOT distribution.
- *Alternative: `headers_setter` extension.* Meant for propagating headers from request context; adds a component for a static value.
- The Collector cannot base64-encode at config time and compose cannot either, so the value is computed where the other secrets are generated (decision 2).

### 2. `LANGFUSE_OTLP_AUTH` lives in `.devcontainer/.env`, generated by `init-env.sh`

- New environments: `init-env.sh` writes it next to the keys it generates.
- Existing environments: `init-env.sh` stops exiting early; if the file exists but has no `LANGFUSE_OTLP_AUTH`, it reads `LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY` from it and appends the encoded value. Nothing else is touched, so other secrets (and the Postgres/Langfuse data that depend on them) stay valid. Encode with `printf '%s' "pk:sk" | base64 | tr -d '\n'` (portable: GNU `base64` wraps at 76 chars, macOS has no `-w`).
- Compose passes `LANGFUSE_OTLP_AUTH: ${LANGFUSE_OTLP_AUTH:?}` to `edot-collector` only. `:?` fails fast at `compose up` instead of starting a Collector that gets 401s.
- *Alternative: store it in the root `.env`.* Rejected: that file is app settings, and the app must not hold Langfuse credentials (AGENTS.md, "Environment files").
- *Alternative: the maintainer appends it by hand.* Rejected: easy to forget on another machine, and the "existing environment" scenario would rely on docs.

### 3. Endpoint over the compose network, plain HTTP

`endpoint: http://langfuse-web:3000/api/public/otel` (the exporter appends `/v1/traces`). Plain HTTP is fine: traffic stays on the compose network, like the app → Collector hop. No `depends_on` on Langfuse: the exporter's default retry and sending queue cover Langfuse starting after the Collector.

### 4. Core decisions for the maintainer (`TODO(human)` in the config)

These shape the pipeline, so the agent leaves them as markers with a short note:

1. **Exporter block.** Write `otlphttp/langfuse` (endpoint, the two headers). Weigh: what `endpoint` means for `otlphttp` (base vs. signal URL, compare with the app's `traces_url`) and whether to set anything beyond the defaults (`compression`, `timeout`, `retry_on_failure`, `sending_queue`).
2. **Keep `debug` in the pipeline?** Options: drop it (Langfuse is the view now, the log stays quiet); keep it at `detailed` (two exporters fan out, handy while the next changes add spans, but every turn floods the log, and later spans will carry message text); or keep it at `basic` (counts only). Spec does not depend on the choice.
3. **Processors.** Langfuse's sample config adds `memory_limiter` and `batch`. Weigh: the app already batches (`BatchSpanProcessor`), and in Collector v0.161 batching is moving into the exporter's `sending_queue`. Adding none is a valid answer for this step; step B adds the redaction processors anyway.

### 5. Verification uses Langfuse UI plus Collector counters

- The `dev` container has no Langfuse keys (by design), so the agent checks delivery through `edot-collector:8888/metrics`: `otelcol_exporter_sent_spans{exporter="otlphttp/langfuse"}` grows and `otelcol_exporter_send_failed_spans` does not.
- The maintainer checks the trace itself at http://localhost:3000 (project Fornada → Tracing). That is the "Pronto quando".

## Risks / Trade-offs

- [Wrong or stale credential gives 401, which `otlphttp` treats as permanent and drops without retry] → the counters show `send_failed_spans`; the Collector log has the HTTP status. The `:?` guard catches a missing value, not a wrong one.
- [Langfuse is slow to start; early spans are retried or dropped] → acceptable in dev; the default queue holds them for a few minutes.
- [Synthetic smoke-test traces now land in the Langfuse project next to real ones] → they carry `service.name=telemetrygen`; filter them out in the UI. Acceptable for a dev environment.
- [Langfuse stores whatever the spans carry] → today only HTTP metadata (route template, status, LLM host); no message text. Later changes that add text attributes must take this into account (phase 6, LGPD map in phase 7).
- [The encoded credential is easy to decode] → it is as sensitive as the secret key itself; it stays in the gitignored `.devcontainer/.env` and the Collector's environment only.

## Migration Plan

1. Pull, then rebuild/restart the dev container: `init-env.sh` appends `LANGFUSE_OTLP_AUTH`, compose recreates `edot-collector` with the new variable and config.
2. Config-only changes after that: restart the Collector from the host (`docker compose -p fornada_devcontainer restart edot-collector`).
3. Rollback: revert the commit and restart the Collector; the extra line in `.devcontainer/.env` is harmless.
